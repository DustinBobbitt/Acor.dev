Why identity matters

The request and its output must describe the same work.

Jobs can change between planning and generation. Work may already be claimed, produced or completed. A re-cut may intentionally repeat output that normal rules would reject. The implementation separates a read-only planning phase from the guarded write phase so those decisions are visible before files appear.

Plan before write

The planner resolves exact job and item identities, determines which rows remain eligible and produces a plan hash. Execution rechecks the contract. A stale or materially changed request must be reconsidered instead of silently generating a different set.

Duplicate and re-cut intent

Existing output and completed-work evidence are not ignored. Repeating work requires an explicit reason or acknowledgement. The goal is not to prevent re-cuts; it is to make their intent distinguishable from accidental duplicate generation.

Receipt after verification

The receipt is not written merely because a generator returned success. Expected artifacts are inspected for existence, size and identity first. The resulting record provides a durable bridge between the approved request and the produced files.

Boundary

Receipt is not completion

A verified generation receipt proves file identity. It does not prove dispatch, station load, machine execution, physical quality or ERP completion.
